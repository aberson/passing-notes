Rule text (draft wording for the protocol and lane rules)

Topology. Notes stay inside a project. A note crosses a project boundary only
between the workspace main (lane main of project dev) and a project's main, in either
direction:
  down:  post --project <P> --from-project dev --from main --to main
  up:    post --project dev --from-project <P> --from main --to main
to: all and to: operator never cross a boundary. A work lane never posts outside its
project; a project main never posts to another project; dev main reaches another
project's work lanes only through that project's main, or by standing in as it.

Seeing. A lane lists only its own project's folders. The one exception is dev main
(or the operator in a terminal): it may run the read-only all-projects view
(passing-notes status --all-projects). That view reads cards, note headers, ack and
binding file names and queue records. It never shows a note body
(never prints, returns or keeps one) and writes nothing.

Stand-in. A project with no live main card may have dev main stand in. Your window
sets a card in that project as lane main (item "stand-in from dev main") and binds
there. It is then that project's main for every rule. When the project gets its own
main window, that window reopens main under the same id and binds itself. The stand-in
stops acting for the project.

Your word, two hops. When you give dev main words for a project, dev main posts
them to that project's main as an operator-relay with the operator-said: first line.
The project main accepts it as your word (sender dev/main, first line operator-said:)
and relays it verbatim to its lanes under section 4. A lane's operator-decision goes
to its project main. If you are not in that window, the project main forwards it up to
dev main verbatim, and your operator-said: answer comes back down the same way. A lane
still accepts operator-said: only from its own project's relay.

Where today's central fits

By role, central already is dev main: one operator window that coordinates several projects. In four of them it stands in for a closed project main. What has to change is the name. The vision gives each project exactly one lane that dev main talks to, so the CLI check can say main and need no per-project lookup. A separate central id would need a record, in every project, of which lane counts as main, and that record could drift.

Q1. May a project main post up to dev main?

Your sentence says project mains talk only to their own lanes. But a reply to dev main, a handoff, or a question you need to answer has to cross back up.

Recommended: yes, the "up" path only, to dev main and nowhere else. Without it, dev main's questions to a project could never be answered. Alternative: none. Dev main would have to read the answers itself through the status view, which never shows bodies.

Q2. What lane id does your window use?

Recommended (A): main everywhere. Your window is dev/main. Where it stands in, it is also <P>/main. Lanes always address main, the CLI check stays a constant, and project defaults (section 8: "unnamed roles fall to main") just work.
Alternative (B): keep central as the stand-in id. Each project then has to record that central counts as its main, and the CLI check needs that record.

Q3. May dev main post straight to another project's work lane?

Recommended: no. It goes through that project's main, or it stands in as that main (then it is in the project, so no boundary is crossed). This matches "communicate with other project main lanes" literally.

Q4. Should the CLI refuse disallowed cross-project posts?

Recommended: yes (exit 2, nothing written). Today two notes from skill-mesh/claude-hygiene to passing-notes all (2026-11-13) show work lanes do post across projects. Under the rule those would be refused, and the sender would go through its main. Alternative: convention only, with a printed warning.

Q5. Does the switch from central to main wait for a quiet point?

Recommended: yes, at your next coordinating-window restart, through /lane-handoff. central hands over to main in each project it holds: a successor with a new id, which fits the existing rules exactly. Lanes opened under central (including lane-status and this one) keep central as their relay until they close. Nothing switches under a live lane. Alternative: switch now, which would interrupt the lanes running today in four projects.
